# 0004. PhET 소스 변경은 버전별 diff가 아니라 「원래 값 찾기 → 토큰 값」 규칙으로 쓴다

## 맥락

같은 공통 파일이 63개 고정 버전에서 제각각이다(예: joist `PhetButton`은 29가지). 원본 PhET 코드와 우리 변경을 구분해 관리해야 하고, 패치가 허용 범위(테마, 학교 표기, 한국어 문자열, 외부 통신 끄기)를 벗어나지 않았음을 검사로 증명해야 했다.

## 결정

패치는 데이터로 적은 규칙이다: 저장소 하나 + 후보 파일 목록 + (정규식 고치기 | 파일 통째 바꾸기) + 필수 여부 + 이유 한 줄. 규칙은 늘 커밋된 원본(`git show HEAD:<파일>`)에 적용하고, 빌드용 임시 슬롯에서만 쓰고, 빌드 뒤 `git checkout --`으로 되돌린다. 종류별로 건드려도 되는 파일은 규칙과 따로 적은 허용 목록이 정하고, 검증이 규칙의 후보 파일·실제로 고친 파일·빌드 뒤 체크아웃 상태를 그 목록과 대조한다.

## 버린 대안

- **버전별 diff 파일**: 63개 × 파일 수만큼 diff가 생기고, 토큰 값을 바꾸면 모든 diff를 다시 만들어야 한다. 어느 diff가 무엇을 바꾸는지 검토하기 어렵다.
- **PhET 저장소를 fork해 고친 브랜치 유지**: 형제 저장소 수십 개 × 버전마다 fork 브랜치가 필요하고, 우리 변경과 원본의 구분이 git 기록 속에 묻힌다.

## 결과

- 토큰을 바꾸면 규칙이 새 값을 그대로 넣으므로 다시 빌드만 하면 된다(`themeHash`가 바뀌어 자동으로 다시 빌드).
- 필수 규칙이 어느 버전에서 맞는 곳을 못 찾으면 빌드가 실패한다. 새 PhET 버전을 들일 때 규칙이 조용히 빠지는 일이 없다. 대신 새 버전마다 `theme/patches/dry-run.mjs`로 규칙을 점검해야 한다.
- 같은 파일을 고치는 규칙은 한 번의 적용 안에서 순서대로 이어져야 한다(그렇지 않아 앞 규칙 결과가 사라진 적이 있다).
- 물리 계산이나 화면 배치를 바꾸는 규칙은 허용 목록 검사에 걸리므로 이 방식으로는 만들 수 없다.
